# Group 2 — Testing & Package Structure Standard

**Status: adopted as the official team standard**, based on Nour's Robust
Regression implementation. Confirmed by the coordinator. Every category
should align its package structure, wrapper naming, test-script pattern,
and report format to what's described below.

**Why this exists:** every category so far has produced a differently
shaped package skeleton and a differently shaped report (a Word doc, a PDF,
an informal write-up with no numeric validation, and this one). That makes
the four/five categories hard to compare and hard to merge into one CRAN
submission. This document describes one shape — package layout, wrapper
naming, test-script pattern, and report format — so every category's output
looks the same and can be reviewed the same way.

Reference implementation (copy the pattern, not necessarily the specific
tests): `fsdabridge/`, `code/test_robust_regression.R`, `code/TEST-REPORT.md`.

---

## 1. Package skeleton

Standard R layout, one skeleton per category is **not** the goal — the goal
is one shared `fsdabridge/` package that every category adds its wrapper
functions and tests into.

```
fsdabridge/
├── DESCRIPTION          # Imports: reticulate; SystemRequirements: MATLAB, FSDA, Python, matlabengine
├── NAMESPACE             # auto-generated by roxygen2 — never hand-edit
├── R/
│   └── engine.R          # copied from code/fsda_engine/engine.R, see note below
├── man/                  # auto-generated by roxygen2 from the @export docs in R/engine.R
├── tests/
│   ├── testthat.R
│   └── testthat/
│       ├── test-offline.R   # runs with NO MATLAB/Python — this is what CRAN's build farm runs
│       └── test-live.R      # skip_if(!nzchar(Sys.getenv("FSDA_LIVE"))) — opt-in, needs MATLAB
└── inst/
    └── python/
        └── engine.py     # copied from code/fsda_engine/engine.py
```

**The one required change when copying `engine.R` into the package:** its
`.engine_dir` lookup normally finds `engine.py` by walking `source()` call
frames, which only works when running a loose script. Inside an installed
package there is no such frame, so this lookup must instead resolve via:

```r
system.file("python", package = "fsdabridge")
```

This is a path-resolution fix only — it does not touch the MATLAB call,
marshalling, or any computational logic in the engine. Every category needs
this same fix; do it once per person copying `engine.R`, not per category.

**Exported function names (the naming that should be shared across the
whole package, not re-invented per category):**

| Function | Purpose |
|---|---|
| `start_engine(routine, python, fsda_root)` | starts the MATLAB engine session |
| `fsda_call(handle, name, ..., nargout, echo_output, options)` | calls any FSDA routine by name |
| `eval_m(handle, expr, nargout)` | evaluates a raw MATLAB expression |
| `stop_engine(handle)` | closes the session |
| `diagnostics(handle)` | R/Python/MATLAB version info for debugging |

These mirror `engine.R`'s own function names 1:1, so there is no translation
layer to keep in sync. If your branch currently uses different names (e.g.
`fsda_start`/`fsda`/`fsda_stop`), rename to match this list — this naming is
now the confirmed standard for the whole package.

## 2. Test script pattern

One `.R` file per category (e.g. `test_robust_regression.R`,
`test_mahalFS.R`, `test_score.R`, `test_mcd_fsmeda.R`), all following the
same shape:

1. **Header comment** stating: which routines are covered, that no
   engine/FSDA code is modified, and the acceptance tolerance (see §4).
2. **Path/env setup** — locate the repo root, default `FSDA_DEV_VENV` and
   `FSDA_ROOT` if unset, `source()` `engine.R` (or `library(fsdabridge)`
   once your category's wrappers are merged into the package).
3. **Shared helpers**, copy verbatim — every category needs the same four:

```r
results = list()
record = function(id, test, status, detail = "") {
  results[[length(results) + 1]] <<- list(id = id, test = test, status = status, detail = detail)
  cat(sprintf("  [%s] %s — %s\n", status, id, detail))
}
one_line = function(msg, width = 200) {
  msg = gsub("[[:space:]]+", " ", msg)
  if (nchar(msg) > width) msg = paste0(substr(msg, 1, width), "...")
  msg
}
finite_ids = function(x) { v = suppressWarnings(as.numeric(x)); v[is.finite(v)] }
attempt = function(expr) {
  tryCatch(list(ok = TRUE, out = expr), error = function(e) list(ok = FALSE, msg = conditionMessage(e)))
}
```

4. **One MATLAB session for the whole script**, started once, reused for
   every call (starting MATLAB is slow — don't restart it per test).
5. **Sections**, each testing one angle, in roughly this order:
   - baseline agreement against a published/independent reference
   - deliberate break attempts (bad shapes, missing values, dimension
     mismatches, tiny samples, invalid option values)
   - anything specific to your routine's own risk areas
6. **Every check ends in one `record(id, description, status, detail)`
   call.** Status vocabulary (use these exact words, so results compare
   across categories):

| Status | Meaning |
|---|---|
| `PASS` | matched the reference within tolerance |
| `CLEAN-ERROR` | bad input rejected safely with a clear error (this is the *correct* outcome for garbage input) |
| `SILENT-OK` | ran without error where a warning/rejection might be expected — needs a human read of the detail column |
| `FINDING` | a real defect — give it a number (see §3) |
| `INFO` | a measurement, not a pass/fail check |

7. **End with a results table print and a one-line summary count**, then
   `stop_engine(h)`.

## 3. Findings numbering

When a test uncovers a real defect (not just an expected clean rejection),
give it a number scoped to your category, e.g. `S1`, `S2`, ... for Score,
`M1`, `M2`, ... for mahalFS — don't reuse `F1`-`F8`, those are already taken
by Robust Regression's findings in `TEST-REPORT.md`. For each:

- **Severity**: High / Medium / Low / Doc gap
- **What happens**, with the actual input and actual output/error text
- **A concrete fix recommendation** for the shared package wrapper (most
  defects found so far are missing input validation that belongs in R,
  before the call ever reaches MATLAB — e.g. checking `is.finite()`,
  checking option ranges, checking types)

---

## 4. Acceptance criterion (same for every category, no exceptions)

A numeric result only counts as agreeing with a reference if the maximum
absolute difference is **≤ 1×10⁻⁹**, same as the project's own agreement
gate (`check_engine.R`). If your routine has no published reference, use:

- an independent R computation over the same data (e.g. compare a summary
  statistic to base R's own function, the way Robust Regression compares
  `FSR`'s beta to `lm()`), or
- a repeat run for determinism, or
- a second, independent tool/package as a sanity check (marked `INFO`, not
  `PASS`/`FAIL`, since it won't agree to 1e-9 — different implementation).

Report the actual numeric difference every time, not just "PASS" — e.g.
"max abs diff 1.8e-15", not "matches."

---

## 5. Report format (`TEST-REPORT.md` per category, or one section each in a combined file)

Same section order every time:

1. Title + one-line scope statement
2. AI-assistance disclosure, if applicable — brief, honest, not hidden
3. Objective (what routine(s), what the coordinator asked for)
4. Acceptance criterion (copy §4 above verbatim)
5. Environment (R/Python/MATLAB versions, OS)
6. How to reproduce (the exact command)
7. Findings (numbered, with severity and fix — see §3)
8. "Verified correct" section — what worked, not just what broke
9. Full test log as a table: ID | Test | Reference | Status
10. One-paragraph summary with the totals (N checks, N pass, N findings)

---

## 6. Git workflow reminder

Fork → your own named branch (e.g. `<name>-<category>`) → push to **your
own fork only** → PR later, targeting **`group2/cran`** on the upstream
repo, never `main`. Don't merge or push directly to anyone else's branch or
fork.
